# V2.5 regimen-first implementation

## Scope

V2.5 reduces the information needed before a user receives a useful NutriClock. The first-run path is now:

1. Enter supplements already chosen by the user.
2. Generate a schedule without requiring meals, coffee, tea, or bedtime details.
3. Show exact times only when the supplied context and active rules support them.
4. Show semantic windows, assumptions, and one highest-value refinement.
5. Answer that single context question and regenerate locally.
6. Offer the existing routine, Today, review, and schedule-adjustment features as follow-on tools.

Routine templates remain available but are not an onboarding prerequisite.

## Architecture

The repository keeps its existing V2 boundaries: `packages/domain` owns deterministic scheduling and rule evaluation, `packages/application` coordinates local persistence and derived views, and web/mobile clients remain thin platform adapters. V2.5 extends the domain contract instead of duplicating logic in either client.

The schedule result now carries:

- `semanticWindow` per item, including flexible, meal-relative, dietary-fat, medication-relative, and beverage-relative concepts;
- `assumptions` for missing but relevant context;
- `completeness`, which describes schedule readiness and is not medical confidence;
- deterministic `questionCandidates` ranked by hard-context impact, refinement value, and stable IDs.

The application exposes `getQuestionCandidates()` and `getNextQuestion()`. Web and mobile use the same one-question refinement behavior. Schedule Repair is represented by `repairSchedule()`, which compares the baseline with the existing adaptive day calculation and reports completed/skipped/preserved/moved states.

The daily clients also expose the repair summary after recorded context changes. The application
derives it from the current day context; it is not persisted. Prior supplement placements are used
only as an in-memory repair hint so an unchanged item is not moved unnecessarily.

Verification hardening rejects malformed day times before adaptive evaluation, keeps warning-only
relationships out of timing summaries, scopes contextual questions to rules that match the entered
product form, and requires an explicit supplement selection before a first-run item can be added.

## Safety decisions

- Medication entries can remain unresolved until the user supplies a usual administration time. No platform assigns one.
- Only active, evidence-resolved rules influence placement, windows, explanations, or questions.
- Clinical and informational rules do not create timing penalties or separation intervals.
- Flexible items have no fabricated morning/evening claim and no public clock time unless the user selected one.
- Generic multivitamins are opaque products; no universal nutrient composition or timing is inferred.
- Unsupported medications remain in the regimen and display limited-coverage guidance. They do not trigger name-based interaction inference.
- Existing review-required rules remain inactive. In particular, unresolved exact coffee/tea and asymmetric interval semantics are not activated by this change.

## Persistence and migration

The canonical persisted envelope remains schema version 1. V2.5 adds no derived schedule fields to persistence, so existing regimen data, routines, overrides, daily logs, and routine templates remain compatible. Regeneration uses the current checked-in ruleset and evidence registry. A corrupt or incompatible local payload continues to surface as a local load error; it is not silently discarded.

## Deliberate non-goals

This implementation does not add supplement or dose recommendations, diagnosis, lab interpretation, treatment advice, unrestricted drug checking, cloud synchronization, analytics, OCR, label capture, or V3 interaction-explorer/change-history features.
